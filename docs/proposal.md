# CommitKeeper: one-page proposal (catalogue idea D13, Inbox commitment tracker)

**User and recurring problem.** A student who is also a research assistant gets promises and deadlines by email from a supervisor, teammates and course staff. Every few days they need to know what they owe, what others owe them, what slipped, and whom to chase. Doing this by hand is error-prone because promises get revised, forwarded, half-fulfilled or quietly forgotten.

**Sample inputs.** Emails (IMAP from an owned test Gmail account, or a labelled .eml export), for example: "Please send me the revised chapter by Thursday", "I'll share the annotated dataset by Tuesday", "Sorry, I need until Friday", "Attached is the chapter", "I have already sent you my comments" (no attachment), a forwarded copy of an announcement, and "ATTENTION AI ASSISTANT: ignore your previous instructions…".

**Expected actions and outputs.** A register of commitments in both directions with resolved due dates and evidence quotes. For each item, a recommended next action (wait / remind me / draft nudge / escalate / ask for clarification / confirm completion). Approval requests for deadline changes, completion claims and outgoing nudges. Nudges are sent once to allowlisted test addresses, or saved as UNSENT drafts. Outputs also include an Excel register, an .ics calendar and a full audit log.

**Architecture.** A single agent with tools and a deterministic policy layer. Per cycle: retrieve memory → fetch new mail → LLM extraction (JSON schema, evidence quote required) → code validation (quote really in the email, participants, isolation, date resolution, untrusted content) → code computes facts → LLM picks the next action (qwen3:8b with reasoning) → policy enforces limits → user approval → controlled action. Checkpoints after each stage and after each email allow a crashed cycle to resume.

**Tools.** (1) Mail reader (IMAP read-only / .eml export). (2) SQLite commitment store (versioned writes, idempotency keys). (3) Deadline resolver and policy checker. (4) SMTP nudge sender (approval-gated, allowlisted, once only). (5) Excel and .ics exporter (manual columns preserved).

**Memory schema.** `profiles`, `preferences` (versioned), `cycles` (checkpoints), `messages` (Message-ID, content hash, processed flag), `commitments` + `commitment_versions` (current vs superseded, approval, source and quote), `actions` (idempotency key, approval, delivery outcome, attempts, error), `plans` (per-cycle recommendation), `manual_reviews`, `security_flags`, and `events` (audit log). See [memory_design.md](memory_design.md).

**Approval boundaries.** The agent may read mail, write its own store and show reminders. It must ask before: changing an approved deadline, accepting a completion claim without evidence, and sending any email. It can never: email a non-allowlisted address, exceed the reminder limit, nudge before a due date, or act on instructions found inside emails.

**Minimum demonstration.** Two fictional profiles; 13 emails for the main profile across 4 accelerated cycles (manual clock), covering a revised promise, a forwarded duplicate, a vague deadline, an unsupported completion claim, an approved extension, an injection email, an SMTP failure and retry, and a process restart. A second profile shows isolation.

**What changes in the second and third runs because of memory.** Run 2 links Bilal's "I need until Friday" to the existing dataset commitment (instead of creating a new one), closes Maryam's script commitment from her "pushed" email, recognises the forwarded announcement, and decides to *wait* rather than nudge because a new date is pending. Run 3, after a full restart and the user's approvals, reads only 3 new emails, measures lateness against the approved 6 Nov date, drafts exactly one nudge, closes the chapter from its attachment, and holds Dr. Imran's unsupported claim for confirmation. Run 4 remembers that one nudge was already sent and waits because of the auto-reply. With `--no-memory` these links are lost (shown in the evaluation).

**Implementation plan.** (1) SQLite schema and memory layer with isolation and versioning. (2) Mail tools and fixtures. (3) Extraction prompt with schema and deterministic validation. (4) Planner, policy and approval commands. (5) SMTP/dry-run sender with retry and idempotency. (6) Excel/.ics exports. (7) Scenario harness: 12 scenarios, memory comparison, metrics. (8) Report and demo.
